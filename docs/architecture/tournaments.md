# Tournament registration and match workflow

Purpose: the end-to-end flow of a tournament in code: lifecycle, registration and payment, brackets, matches, results and disputes, with the services that own each step. Product view: [features](../guides/features.md#tournaments). Models: [data model](data-model.md).

## 1. Tournament lifecycle

`Tournament.status` (`apps/tournaments/models/tournament.py`) moves along `Tournament.ALLOWED_TRANSITIONS`:

```
draft -> pending_approval | published | registration_open | cancelled
pending_approval -> published | cancelled
published -> registration_open | cancelled
registration_open <-> registration_closed ; both -> cancelled
registration_closed -> live | cancelled
live -> completed | cancelled
completed | cancelled -> archived
```

`TournamentLifecycleService` (`apps/tournaments/services/lifecycle_service.py`) performs transitions (`transition`) and time-driven ones (`auto_advance`, `auto_advance_all`): for example `registration_open` closes when `registration_end` passes, and a closed registration reopens if an organizer moves the end date back into the future. `auto_advance_all` is what the cron endpoint `api/lifecycle/cron/` invokes (Celery beat is off). The TOC API also calls `auto_advance` when it loads a tournament.

Formats (`Tournament.FORMAT_CHOICES`): single elimination, double elimination, round robin, Swiss, group + playoff.

## 2. Registration

Service: `RegistrationService` (`apps/tournaments/services/registration_service.py`).

1. **Entry**: `register_participant(tournament_id, user, team_id=None, registration_data=..., is_guest_team=...)` creates a `Registration` (exactly one of `user_id` or `team_id`) after `check_eligibility` (tournament open, not already registered, game identity/passport, team and roster rules). Custom registration form fields are validated by the form services (`form_validator.py`, `smart_registration`).
2. **Payment** (paid tournaments): `submit_payment` / `submit_payment_proof` (manual methods) or `pay_with_deltacoin` (wallet). Staff or organizers use `verify_payment` / `reject_payment`; `refund_payment`, `waive_fee`, `check_auto_waive_eligibility` handle exceptions. `Payment` is 1:1 with `Registration`.
3. **Approval**: `approve_registration` / `reject_registration` (and bulk variants) when the tournament requires organizer approval.
4. **Capacity**: `add_to_waitlist`, `promote_from_waitlist`, `auto_promote_waitlist`, `assign_slot`, `assign_seed`.
5. **Leaving**: `cancel_registration`, `withdraw_registration` (`can_withdraw` decides), `disqualify_registration`.

`Registration.status` values: `draft`, `submitted`, `pending`, `auto_approved`, `needs_review`, `payment_submitted`, `confirmed`, `rejected`, `cancelled`, `waitlisted`, `no_show`. Retried or duplicate requests must not create a second registration or charge twice; keep that invariant when changing these services.

## 3. Check-in, brackets and stages

* **Check-in**: `check_in_service.py` / `checkin_service.py` and `CheckIn`/`TournamentLobby` models; match-level check-in is `MatchService.check_in_participant`.
* **Brackets**: generated by the bracket generators in `apps/tournament_ops/services/bracket_generators/` and `apps/tournaments/services/bracket_service.py`; organizers publish the bracket. Edits are logged (`bracket_edit_log`), and `bracket_recovery.py` / `bracket_repair_service.py` repair broken links (management commands `repair_bracket_match_links`, `repair_bracket_names`). Group stages: `group_stage_service.py`; stages: `TournamentStage`.
* **Live draw**: `ws/tournament/<id>/draw/` and `group-draw/` ([realtime](realtime-and-notifications.md)).

## 4. Matches

`Match.status`: `scheduled -> check_in -> ready -> live -> pending_result -> completed`, plus `disputed`, `forfeit`, `cancelled`. `MatchService` (`apps/tournaments/services/match_service.py`):

| Step | Method |
|---|---|
| Create | `create_match` |
| Check in | `check_in_participant` |
| Start | `transition_to_live` |
| Participant result | `submit_result(match, participant scores, ...)`; the opponent calls `confirm_result` |
| Dispute | `report_dispute` -> `resolve_dispute` / `escalate_dispute` |
| Organizer actions | `organizer_submit_score`, `organizer_override_score`, `organizer_reschedule_match`, `organizer_forfeit_match`, `organizer_cancel_match`, `forfeit_match`, `cancel_match` |
| Guards | `winner_correction_block_reason` (a score correction cannot change the winner once the next round or the tournament is decided), `reset_block_reason`, `draws_allowed_for_match` |

`match_authority.py` decides who may act. Disputes are `DisputeRecord` rows with evidence uploads (`DisputeEvidence`, private media) and notes; `dispute_service.py` implements the workflow.

## 5. Completion and rankings

Once a tournament is `completed`, `CompletionPipeline.run` (`apps/tournaments/services/completion_pipeline.py`) performs isolated steps (one failing step does not stop the others): final standings, winners and prize allocation, certificate generation (`certificate_service`), analytics snapshot and participant notifications; it returns a `CompletionReport` with counts and errors. The public results page shows only verified results. Competitive rankings (`apps/competition`) are built from `MatchReport` / `MatchVerification` records and ranking snapshots; `compute_initial_rankings` and `run_vnext_rank_jobs` rebuild them.

## 6. Organizer console (TOC)

`api/toc/<slug>/...` (`apps/tournaments/api/toc/`): overview, participants, payments, brackets, matches, disputes, lobby, check-in, announcements, rosters, rules, staff/RBAC, analytics, audit. Access rule: [auth and permissions](auth-and-permissions.md#authorization). Typical debugging path for a stuck tournament: check `Tournament.status` and dates, run the lifecycle service in a shell (`TournamentLifecycleService.auto_advance(t)`), inspect `Registration` statuses and `Match` rows, then the repair commands above.
