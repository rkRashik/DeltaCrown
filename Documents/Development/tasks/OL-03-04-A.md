## Confirmed unnecessary work

1. **Unused view context.** [home()](../../../apps/siteui/views.py) calls [get_homepage_context()](../../../apps/siteui/homepage_context.py) before building `v3` extras. It assembles old stats, games, teams, tournaments, testimonials, FAQs and a content model. The active template consumes `v3`, `home_ui`, `hero_ctx` and static section data. Local template resolution read none of the legacy view keys. Removing only those keys from the synthetic render context preserved identical HTML in all three tested cases, with a fixed synthetic CSRF token.
2. **Unused render-time legacy context.** [common homepage_context](../../../apps/common/context_homepage.py) is registered in [TEMPLATES](../../../deltacrown/settings.py). It runs for `/` even though the current template does not consume its `homepage` key. It builds six games' tournament/player counts plus feature/live/upcoming data. This work falls inside the logged render phase and uses a separate 60-second cache.
3. **Cached false treated as a miss.** [nav_context](../../../apps/siteui/nav_context.py) converts the live-cache value to bool and rebuilds whenever false. A valid cached False therefore still causes an existence query and cache write. The warm synthetic guest case reproduced one SQL dispatch despite zero cache misses.

The first two findings establish avoidable serial work on cache misses. Production telemetry establishes that the corresponding stages can be slow. Exact attribution of every millisecond to SQL execution, network, Redis or Python is not available.

## Database, cache and template behavior

| Path/key | Source behavior |
|---|---|
| `homepage_context_v2` | Shared legacy context, 300 s TTL; includes a model instance and materialized lists. Cold build duplicates newer reads. The singleton getter can create a row if missing; it was never invoked against a real DB in this task |
| `homepage_extras_v3` | Shared public display dict, 600 s TTL; current page data. Guest/auth hero is resolved separately |
| `common:homepage_context:v1` | Legacy global processor, homepage-only, 60 s TTL; direct cache calls bypass safe-helper cooldown |
| `siteui:site_settings:v1` | Global processor, 60 s TTL; feature/stats/spotlight/timeline work occurs during render even when individual values are unused |
| `context_active_games` | Global games context, 60 s TTL; direct cache calls |
| Navigation | Live flag 30 s; live count 60 s; some authenticated values are per-user. False-value handling causes the demonstrated extra warm query |

- `cache_safe` catches get/set failures and skips subsequent helper calls for 60 seconds after failure. The first failing operation can still wait. Source defaults individual Redis connection/read timeouts to 2 s and permits timeout retry; this is not a 2 s total-request bound. Direct cache users do not inherit that circuit breaker. No matching failure logs were returned for the measured window; **Redis as the dominant cause is unverified**.
- No cache-hit/miss/operation-time telemetry exists in the phase log. No live keys, payloads or TTLs were read. Production hit rate, eviction, RTT and serialization cost remain unknown. The synthetic pickle sizes were approximately **9.8 KB legacy / 11.3 KB extras**; these are fixture sizes, not production payload measurements or evidence of a serialization bottleneck.
- `_hero_stats()` issues four tournament counts and two prize aggregates separately, plus user/team/game counts. Combining compatible aggregates is a future opportunity, not an implemented change.
- `_quick_jump()` calls `_game_posters()`, then `get_homepage_extras()` calls it again. Each nonempty build already uses one game read plus two grouped count queries; reuse could avoid three duplicate dispatches. **Game counts and top-team win/loss calculations are already batched**, so do not label these loops a per-game/per-team N+1.
- `_upcoming_cards()` still counts registrations separately per returned tournament: an N-dependent read path. Existing `select_related()` protects its game access. Batch counts must preserve status/deletion/slot semantics.
- Authenticated hero probes repeat team identity discovery across pending/active/registered checks. Guest hero exits without SQL. Notifications already reuse a request-level unread-count attribute; the compatibility context processor is not automatically a second count query.
- Pooled DB connections default to `CONN_MAX_AGE=0`, SSL and health checks. Remote connection/round-trip overhead is plausible, but actual Render overrides, connection setup time, query plans and SQL execution times were not measured. Do not increase connection lifetime blindly.
- Presentation and static sections are pure Python. Current `v3` output is materialized scalar/list data; no template-loop SQL occurred in the tested fixture. Other populated branches need real isolated DB verification. Render timing includes global processors, so it is not a pure HTML/CSS CPU measurement.

**Recommend ONE first implementation: OL-04-B, remove only the unused `get_homepage_context()` invocation from `apps/siteui/views.py:home`.** Initialize the view context without that legacy payload and retain extras, per-request hero, presentation, static sections, SEO and `never_cache`. Estimated outcome: eliminate the legacy builder's work and its cache access. The **1.2-2.5 s** observed context-stage range is an opportunity bound on those slow observations, not a predicted request saving: shared Redis/DB waits could move to the next builder instead. Cache-hit savings are smaller; overall p50/p95 improvement is unknown. No additional service/cost or memory-heavy cache is required; expect less temporary allocation, with amount unmeasured. Deploy risk is missing implicit context consumers, so verify those before approval.

## Remaining unknowns and stability conclusion

Actual production SQL counts/plans/time, pooler/Redis RTT, hit rates, stampedes, per-request CPU/throttling, active thread counts and request concurrency remain unverified. One Daphne invocation/instance and worker-OFF evidence does not establish a global concurrency limit. Earlier health failures deserve separate follow-up if they recur. Render Free idle spin-up can add delay ([provider reference](https://render.com/docs/free)), but no cold-start experiment was performed and returned events show no restart/deploy in the slow-log window. Multi-second application phases therefore cannot all be dismissed as platform wake-up time.

The current evidence supports removing redundant synchronous work before buying capacity, changing workers or moving media. It does not prove that all remaining latency is database execution or that CPU, Redis and cold starts never contribute. No production performance improvement occurred during this investigation.
